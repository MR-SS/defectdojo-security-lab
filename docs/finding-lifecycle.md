## Finding removal scenario design

This scenario is design-only until separately approved. It uses the same parser, test type, service context, and explicit options for all submissions:

1. Import a report containing A, B, and C.
2. Reimport a report containing A and C, with `close_old_findings=true`, `close_old_findings_product_scope=false`, `do_not_reactivate=false`, and a recorded deduplication execution mode.
3. Read the target Test and all candidate findings in the affected Engagement before and after each operation.

Controlled variables: parser, target Test, Engagement, Product, test type, service (unset unless deliberately included), severity threshold, identity fields, and deduplication algorithm. The A/C report entries retain their original `unique_id_from_tool`; B is absent.

## Exact 3.5.101 behavior derived from pinned source

`DefaultReImporter.process_findings()` records original findings from the target Test and identifies unmatched original IDs as candidates for mitigation. `close_old_findings()` only acts when its toggle is true. It derives present hash codes and `unique_id_from_tool` values from non-mitigated report findings, then delegates scope selection to `get_close_old_findings_queryset()`.

For reimport, matching candidates are selected against the same Test. The configured algorithm selects by hash code, `unique_id_from_tool`, either identity, or legacy title/severity behavior. A previously mitigated matching finding is eligible for reactivation unless `do_not_reactivate` is true.

The close-old query begins with active or risk-accepted findings of the same test type, excluding the current Test. It excludes report-present findings according to the resolved deduplication algorithm. Default scope is the current Engagement; `close_old_findings_product_scope=true` broadens to the Product. It additionally restricts by Service: a service-specific run closes only the same Service; an unset service closes only null/empty-Service candidates. Matching findings are mitigated with an automatic-close note and locations are updated.

For the narrowly proposed A/B/C removal experiment, B is expected to be mitigated only if it falls within that query scope. A and C must remain active. The current Test itself is excluded by the cross-test close-old queryset, so this source path is not equivalent to “remove B from the same Test”; the approved experiment must capture actual importer return counts and relevant sibling-test state before claiming behavior. This is a potential design/semantic ambiguity, not a regression.

Deduplication execution mode controls post-processing scheduling. `async_wait` waits for dispatched post-processing before response accounting; other asynchronous modes do not make the close-old selection synchronous by themselves. Evidence must capture the requested mode and importer result counts.

## Failure classifications and evidence

- FAIL: an observed result contradicts the pinned-source-derived scope and has been independently repeated.
- INCONCLUSIVE: scope, service, algorithm, asynchronous completion, or API response is insufficiently observed.
- BLOCKED: the required separate approval for a removal mutation is absent.

Capture sanitized request flags, fixture hashes, import response summaries, Test/Engagement/Product IDs, normalized findings before and after, importer counts for new/closed/reactivated/untouched where available, resolved deduplication configuration, and bounded worker logs if asynchronous work is selected. Never retain tokens, credentials, or unredacted authorization headers.

No cleanup is authorized: Product, Engagement, Tests, and findings remain after any future experiment.
